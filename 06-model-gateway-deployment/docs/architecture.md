# 架构设计文档

## 1. 整体架构

本项目采用**分层架构**设计，从下到上分为四层：

```
┌─────────────────────────────────────────────────────┐
│  L4 业务应用层                                        │
│  角色引擎 / RAG / Agent / 各种 LLM Apps               │
├─────────────────────────────────────────────────────┤
│  L3 网关中间件层                                      │
│  限流 / 降级 / 灰度 / 计费 / 审计                     │
├─────────────────────────────────────────────────────┤
│  L2 模型网关层                                        │
│  LiteLLM Proxy - 模型抽象 / 统一 API / 路由           │
├─────────────────────────────────────────────────────┤
│  L1 模型服务层                                        │
│  云端 API / vLLM / Ollama / 其他推理框架              │
└─────────────────────────────────────────────────────┘
```

### 各层职责

| 层级 | 职责 | 关键技术 |
|------|------|----------|
| L4 业务应用 | 具体的 AI 功能实现 | FastAPI / LangChain / LangGraph |
| L3 网关中间件 | 业务级治理（限流、降级、灰度、计费） | FastAPI + Redis |
| L2 模型网关 | 模型抽象、协议转换、统一接口 | LiteLLM Proxy |
| L1 模型服务 | 模型推理本身 | vLLM / Ollama / 云端 API |

## 2. 核心设计思想

### 2.1 模型抽象（Model Abstraction）

业务代码不直接依赖具体模型，而是依赖**模型别名**：

```python
# ❌ 不好：硬编码具体模型
client.chat.completions.create(model="gpt-4o-mini", ...)

# ✅ 好：使用网关定义的业务别名
client.chat.completions.create(model="chat-default", ...)
```

**好处：**
- 换模型只改网关配置，不用改业务代码
- 可以根据场景选择不同等级的模型（chat-lite / chat-default / chat-pro）
- 便于做灰度发布和 A/B 测试

### 2.2 降级链（Fallback Chain）

每个业务模型别名对应一个**降级链**，当前面的模型失败时自动尝试下一个：

```
chat-default:
  1. gpt-4o-mini   (主模型，性能好)
  2. qwen-turbo    (第一降级，便宜)
  3. deepseek-chat (第二降级，备选)
  4. chat-local    (最终降级，私有化部署)
```

**降级触发条件：**
- HTTP 5xx 错误
- 请求超时
- 限流错误（429）
- 连续 N 次失败后的熔断

### 2.3 限流策略（Rate Limiting）

采用**多级限流**，基于滑动窗口算法：

```
QPS 限制 (每秒) → RPM 限制 (每分钟) → Daily Token 限制 (每天)
```

**限流维度：**
- 按 API Key
- 按用户 ID
- 按模型
- 按 IP（可选）

**为什么多级？**
- QPS 防止突发流量打垮服务
- RPM 平滑短时间内的波动
- Daily Token 控制总体成本

### 2.4 灰度发布（Canary Release）

新模型上线时，通过灰度机制逐步放量：

```
新模型上线流程:
  1. 0% 流量 → 内部测试
  2. 5% 流量 → 小范围验证
  3. 20% 流量 → 扩大范围
  4. 50% 流量 → 半量
  5. 100% 流量 → 全量上线
```

**灰度规则：**
- 白名单用户 → 强制走新模型
- 黑名单用户 → 强制走旧模型
- 其他用户 → 按比例随机分配

## 3. 关键技术选型

### 3.1 模型网关：LiteLLM

**选型理由：**
- 支持 100+ 种模型，生态最丰富
- OpenAI 兼容接口，业务层零改动
- Python 生态，容易二次开发
- 内置限流、缓存、降级等功能
- 活跃的社区维护

**替代方案对比：**

| 方案 | 优点 | 缺点 |
|------|------|------|
| LiteLLM | 生态最全、Python 友好 | 性能一般（够用） |
| One API | 界面好、Go 语言性能好 | 二次开发需要 Go |
| 自研网关 | 完全可控 | 开发维护成本高 |

### 3.2 推理框架：vLLM

**选型理由：**
- PagedAttention 技术，显存利用率高
- 连续批处理，高并发吞吐量大
- OpenAI 兼容 API，接入简单
- 支持多种量化（AWQ / GPTQ / FP8）
- 社区活跃，更新快

**替代方案对比：**

| 方案 | 特点 | 适用场景 |
|------|------|----------|
| vLLM | 性能最好、功能最全 | 生产环境高并发 |
| Ollama | 最简单、跨平台 | 开发测试、个人使用 |
| TGI | HuggingFace 官方 | HF 生态深度用户 |
| llama.cpp | CPU 也能跑 | 边缘设备、无 GPU |

### 3.3 限流存储：Redis

**选型理由：**
- 高性能，适合做限流计数器
- 原子操作支持好（INCR / ZADD）
- 过期时间 TTL 原生支持
- 可以复用作缓存和会话存储

## 4. 成本控制策略

### 4.1 模型分层策略

```
┌─────────────────────────────────────────┐
│              chat-pro (高质量)            │  复杂任务：代码、分析、创作
│            (GPT-4o / Claude)             │
├─────────────────────────────────────────┤
│            chat-default (均衡)            │  普通对话：日常聊天、问答
│          (GPT-4o-mini / Qwen)            │
├─────────────────────────────────────────┤
│             chat-lite (低成本)            │  简单任务：分类、摘要、提取
│         (小模型 / 量化模型)               │
├─────────────────────────────────────────┤
│             chat-local (私有化)           │  敏感数据：内部文档、隐私对话
│        (vLLM 私有部署模型)                │
└─────────────────────────────────────────┘
```

### 4.2 Prompt 优化

- **System Prompt 优化**：精简不必要的描述，减少每轮开销
- **Few-shot 示例精选**：只保留最关键的示例
- **历史消息压缩**：超过 N 轮后自动总结旧消息
- **缓存常用 Prompt**：前缀缓存（Prefix Caching）

### 4.3 推理优化

| 技术 | 原理 | 效果 |
|------|------|------|
| KV Cache | 缓存 Attention 的 K/V 值 | 多轮对话速度提升 2~5x |
| PagedAttention | 分页管理 KV Cache | 显存利用率提升 2~4x |
| 连续批处理 | 请求级别动态批处理 | 吞吐量提升 10~100x |
| 量化（AWQ/GPTQ） | 降低权重精度 | 显存减少 50~75% |
| 投机采样 | 用小模型草稿 + 大模型验证 | 解码速度提升 2~3x |

## 5. 可观测性设计

### 5.1 关键指标

**业务指标：**
- 请求量（QPS / RPM / 日活）
- Token 用量（输入 / 输出 / 总量）
- 成功率 / 失败率
- 延迟分布（P50 / P95 / P99）
- 各模型使用占比

**成本指标：**
- 每日 / 每月花费
- 平均每次请求成本
- 各模型成本占比
- 预算使用进度

**系统指标：**
- GPU 利用率
- 显存使用率
- KV Cache 命中率
- 队列长度

## 6. 安全设计

### 6.1 API Key 管理
- 网关统一管理 Key，业务方不接触底层模型 Key
- 支持 Key 的创建、吊销、配额设置
- 按 Key 维度统计用量和成本

### 6.2 数据安全
- 敏感数据走私有化部署模型，数据不出内网
- 请求和响应日志脱敏
- HTTPS 传输加密

### 6.3 防滥用
- 速率限制防止恶意调用
- 异常请求检测（短时间大量请求、异常长 Prompt）
- 内容安全审核（可选，接入审核模型）
